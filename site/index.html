Posting Triage

The LLM reads, code decides.

Reads a job posting and answers APPLY, FLAG, SKIP, or DEAD, with a one-line reason quoted from the posting itself.

Code on GitHub Design doc Deploy guide

The problem

Applying to a posting that was never a fit costs a tailored resume, sometimes a cover letter, then often an automatic rejection. Filtering by hand or by keyword falls short in three ways:

  • Keywords miss the fields that matter. Role level, degree, years of experience, graduation window, and location are written in sentences, not titles. "2+ years preferred" is sometimes a real cutoff and sometimes not.
  • Dead links waste time. A closed posting can hide a careers page with other roles worth applying to.
  • An LLM's verdict alone can't be checked. Asked "should I apply?", a model gives an answer and a reason in its own words, with no way to tell a real reason from an invented one.

How it works

  1. Is it live? Greenhouse, Lever, Ashby, and Workday links go through their job-board APIs; anything else opens in headless Chromium (Playwright). A removed posting returns DEAD plus the company's careers page. A page that can't be read is FLAG ("couldn't verify"), never a guessed DEAD.
  2. Claude fills a form. Role type, level, degree, graduation window, experience, location, and track, each with the exact quote it came from, or null if the posting is silent.
  3. Code checks every quote. If a quote isn't in the posting, the model gets one retry; if it fails again, that value can't decide anything.
  4. Rules decide. Plain Python compares the fields with the applicant's profile. Every rule runs, any SKIP beats any FLAG, and the verdict names the deciding field and its quote.

Apply precision: of the postings an approach said to apply to, how many it should have. Right reason: the verdict and the deciding field are both right. Direct prompt: the LLM gives the verdict itself, built only as a comparison. Cost: the whole run, 200 synthetic plus 5 real postings, at batch price.

  • Any LLM approach beats keyword rules: 56% → 94–100%. Keyword rules have no FLAG, so every posting that needed a human look was answered wrong.
  • The pipeline scored 100% on every model; the direct prompt depended on the model. Most of Sonnet's direct misses broke the decision order rather than misreading the posting. In the pipeline that order is tested code.
  • Haiku is the default: it ties the best score at about 1/20 the cost of Opus.

Why not just ask an LLM? On this benchmark, accuracy alone doesn't justify the pipeline. The case is what accuracy doesn't measure: its reasons are guaranteed to be in the posting (the direct prompt quoted correctly in all 377 of its quoted answers, but nothing checks that), its rules can't drift between models, and a wrong answer points at one misread field you can test and fix.

How far to trust it: synthetic scores are an upper bound. Only 5 real postings are hand-labeled so far; every LLM approach got all 5 right and the baseline got 3, but all 5 are SKIPs, so they can't measure apply precision.

Deployment

Open the architecture diagram full size

  • One Docker image runs both the CLI and the FastAPI REST API, as a non-root user. On Lambda, the Lambda Web Adapter turns each request into an ordinary HTTP call.
  • AWS Lambda (arm64, 2 GB) behind a function URL; image in ECR; secrets and profile in Parameter Store; logs in CloudWatch; a least-privilege IAM role; a $5 budget alert.
  • A patched image: removing Chromium's unused media libraries took the registry's vulnerability scan from 337 findings to 0.
  • Deploys run from a Mac with one script and temporary credentials, so no long-lived AWS keys exist anywhere.
  • Speed on Lambda: a new copy of the function starts in about 16 s, and its first Chromium posting takes about 30 s; after that, a triage takes about 3–11 s.

Security

The API is private: every triage spends money on the Claude key and runs a browser on a server, so this page shows recorded results and makes no live AI calls.

  • Bearer token, compared in constant time; the server won't start without one.
  • Limits: 10 requests a minute per token in each running copy of the function (up to 2 copies, so 20 a minute at most), a 90 s timeout, and at most 2 triages at once.
  • No server-side request forgery: only public http(s) URLs on ports 80/443, with every resolved address checked. Chromium's traffic goes through a filtering proxy that re-checks redirects, iframes, and page resources, so the cloud metadata address (169.254.169.254) gets a 400.

Testing

1,490+ unit tests (no network, no API calls), 6 headless-browser tests, and a 10-check Docker smoke test. GitHub Actions runs the unit tests on Python 3.11 and 3.13, and builds and smoke-tests the arm64 image, on every push.
